## Summary

The ticket reports Prod 500s on 2025-04-24 attributed to many users idling on
the View Alerts page, with the `list_all_paginated` query "piling up." It has
**no acceptance criteria** (the AC section is an empty list item) and **no
measurable performance target** ("If we can make the query more efficient
hopefully this won't happen again"). Steps to Reproduce point only to a
production Splunk log, which is not reproducible in a QA environment.

The fix is **PR #1036 — "reduce list_all_paginated calls on view alerts mount"**
(commit `c6e847c3`, ~4 weeks ago, on `main`), which reduces how often the
expensive query runs during page load:

- `mount/3` no longer runs `list_all_paginated` at all — it assigns `alerts: []`
  and an empty `%Flop.Meta{}`.
- A new `handle_params/3` clause short-circuits on the **dead/disconnected
  static mount** (`%{transport_pid: nil}`) with `{:noreply, socket}`, so the
  static render issues **zero** `list_all_paginated` queries.
- The periodic `:update` poll is now scheduled **only when `connected?(socket)`**
  (previously scheduled on every mount, including the dead mount).

This is verified at the code/behavior level. It is a **conditional pass** rather
than a full pass because the original symptom (query pile-up under concurrent
idle load) cannot be reproduced or measured against a target — the ticket gives
neither acceptance criteria nor a performance threshold, and the repro is a Prod
log I cannot access.
