# QA Report — 🐛 Don't store/show Direction field when not relevant

- **Ticket:** [1212433843572811](https://app.asana.com/1/15492006741476/project/1167196461144361/task/1212433843572811)
- **Environment:** dev-green (`https://alerts-manager-dev-green.mbtace.com/`) for browser evidence; local test DB (branch `jy-claude-skill`, checkout serving the fix commit `34cc7454`) for the ExUnit regression test
- **Mode:** write-test
- **Verdict:** **conditional pass**

## Summary

The fix (commit **34cc7454**, PR #1002, authored 2026-05-08) limits stored
directions to the only service/effect combinations whose form actually has a
Direction field (`:RDS`, `:RDT`, `:RDTS`). For Stop→Route (`:SR`), Route (`:R`),
Facility, and Systemwide alerts the builder now stores **no** direction, so
"Both" never reaches the modal "Direction:" row or the history CSV for any new
or re-edited alert. This is verified against current code and on dev-green.

The verdict is **conditional** because:
- dev-green is read-only, so the live create/edit `/mono/` repro flow could not
  be exercised there; current-code behavior was instead pinned with ExUnit.
- The ticket's cited Alerts-Manager example alert **#1551248 no longer exists**
  on dev-green (searched in the All timeline; not found).
- The fix is at the **storage layer only**. Legacy alerts that already persisted
  `["Both|default"]` (created before 2026-05-08, or IBI-imported variants) still
  render "Direction: Both" — confirmed by two pre-fix `:R` alerts on dev-green
  (#1000000, #1000016, both created 2026-03-02). The ticket's own AC notes
  acknowledge that rewriting stored data was considered out of scope.

## Acceptance criteria

### AC #1 — Stop→Route / Route / Facility / Systemwide never store or show a direction — **pass**

- Stop→Route test case (Bus • Stop Move): four dev-green alerts (#696723, #691294, #679938, #672170) all show **no** Direction field.
  ![Stop Move modal](evidence/stop-route-stopmove-696723-modal.png)
- Route test case (Ferry • Extra Service paradigm = `:R`): proven against current code by ExUnit — `AlertBuilder.build_alert(_, :R, _)` returns `original_direction_selections in [nil, []]` even when a `direction` value is present in the form data. (No Ferry • Extra Service alert exists on dev-green; `:R` is the same code path.)
- The two dev-green `:R` alerts that DO show "Direction: Both" (#1000000, #1000016) were created **2026-03-02, two months before the fix (2026-05-08)** — genuine pre-fix legacy data, not current-code behavior.
  ![Legacy Route Both modal](evidence/skeptic-1000016-both.png)

### AC #2 — If `original_direction_selections` is "Both", don't show the direction field — **conditional pass**

- For new/edited alerts the fix prevents "Both" from being stored for non-direction combinations, so the modal's `if @direction_names != ""` guard never fires for them.
- The IBI both-directions example (#687296) correctly shows no Direction field.
  ![IBI both-directions modal](evidence/ibi-both-687296-modal.png)
- **Gap:** the modal rendering layer (`lib/alerts_ui_web/components/review_modal.ex:206`) was **not** changed — it has no "Both" filter, only an empty-string check. A legacy alert with `["Both|default"]` still renders "Direction: Both" (#1000000/#1000016). Per the ticket's AC notes, retroactively scrubbing stored "Both" was treated as out of scope.

### AC #3 — Don't output "Direction: Both" in the history .csv when direction is both — **conditional pass**

- Verified against current code: `AlertHistory.build_history/1` with an empty or `nil` `original_direction_selections` produces affected-entities text with **no** "Direction" segment.
- **Gap (pinned by test):** `AlertHistory.build_direction/1` renders any single stored direction name verbatim, so a legacy `["Both|default"]` value still yields "Direction: Both" in the CSV. The fix is storage-side, not renderer-side.

## Skeptic pass

One refutation pass (`1212433843572811-skeptic.mjs`) with two lenses:
- **Data-state lens:** inspected additional Stop→Route alerts — all correctly omit Direction, so #696723 is representative, not a fluke.
- **Exact-value lens:** re-confirmed #1000016 and additionally found #1000000 showing "Direction: Both". Cross-checked creation dates (2026-03-02) against the fix date (2026-05-08): both predate the fix, classifying them as legacy data rather than a current-code regression. Refutation did not overturn the verdict.

Test-sensitivity check (skeptic on the test itself): the pre-fix diff built
`user_selected_directions` whenever routes were non-empty; the `:R`/`:SR` tests
pass non-empty `route_ids` **and** a `direction`, so they would have failed on
pre-fix code — the tests genuinely exercise the fix rather than passing trivially.
The `:RDS` control test confirms the fix does not over-correct (legitimate
directions are still stored).
